# WORKFLOW: Архитектор

Статус этапов ниже: PROPOSAL, требует подтверждения пользователя.

## Фаза 0. Старт и discovery
Вход: запуск агента.
Действия:
1. Запросить адрес папки проекта.
2. Выполнить DISCOVERY_SKILL.md: прочитать docs_setup, agents, Agent_Memory.
3. Классифицировать информацию: USER REQUIREMENT, CONFIRMED DECISION, PROPOSAL, ASSUMPTION, OPEN QUESTION, CONFLICT.
4. Создать или обновить `Agent_Memory/_Shared/` и `Agent_Memory/Architect/`, если их нет.
Выход: discovery-отчёт и список блокирующих вопросов.
Блокеры: нет адреса папки, нет docs_setup, нет описания стека.

## Фаза 1. Сбор входных данных
Действия:
1. Собрать план Продюсера, реестр ассетов Художника, реестр звуков Саунд-дизайнера.
2. Для каждого недостающего фрагмента создать запрос в `_Mailbox/<Agent>/` со статусом OPEN.
3. Зафиксировать OPEN QUESTION в OPEN_QUESTIONS.md Архитектора.
Блокирующие данные: стек, план этапов. Остальные данные можно уточнять по ходу.
Выход: входной пакет, список запросов.

## Фаза 2. Архитектура
Действия:
1. Описать модули, сцены/экраны, управление данными, сохранения, интеграцию ассетов и звуков.
2. Предложить 1-2 варианта спорных решений, если они есть. Выбор фиксирует пользователь.
3. Записать ARCHITECTURE.md и DECISION_LOG по каждому утверждённому решению.
Выход: ARCHITECTURE.md.
Точка проверки П1: пользователь подтверждает архитектуру.

## Фаза 3. Среда разработки и репозиторий
Действия:
1. Описать среду в ENVIRONMENT.md: версии, инструменты, команды установки.
2. Получить подтверждение пользователя на установку инструментов.
3. Установить инструменты и создать структуру репозитория, .gitignore, шаблоны конфигов.
4. Проверить установку командой сборки или проверки и записать результат.
Выход: ENVIRONMENT.md, структура репозитория, отчёт о проверке среды.
Точка проверки П2: пустой проект собирается по ENVIRONMENT.md.

## Фаза 4. Инструкция для Разработчика
Действия:
1. Разбить работу на этапы в DEV_INSTRUCTIONS.md. Для каждого этапа: цель, задачи, входы, выход, критерии готовности, способ проверки.
2. Передать Разработчику через `_Mailbox/Developer/`.
Выход: DEV_INSTRUCTIONS.md, уведомление Разработчику.

## Фаза 5. Выполнение и проверки этапов
Цикл для каждого этапа:
1. Разработчик выполняет этап и пишет статус в TASK_BOARD.md и отчёт в `_Mailbox/Architect/`.
2. Архитектор читает отчёт и вопросы, отвечает в `_Mailbox/Developer/`.
3. Архитектор проверяет критерии этапа и пишет отчёт о проверке по OUTPUT_CONTRACT.md.
4. При успехе этап переходит в DONE. При провале этап возвращается с замечаниями. При частичном выполнении статус PARTIAL.
5. Переход к следующему этапу без решения пользователя запрещён, если он помечен как точка проверки.

Этапы по умолчанию (PROPOSAL):
- E0. Среда и репозиторий собираются.
- E1. Каркас приложения запускается, пустая сцена или экран открываются.
- E2. Базовый игровой цикл и управление.
- E3. Интеграция ассетов Художника.
- E4. Интеграция звуков Саунд-дизайнера.
- E5. Сборка релиза-кандидата.

Точки проверки: после E1, E3, E5 пользователь подтверждает переход (PROPOSAL). Остальные проверяет Архитектор по критериям.

## Фаза 6. Правки кода Архитектором
Вызывается, когда для работы среды нужна небольшая правка кода (см. SYSTEM_PROMPT.md, раздел «Правки кода»).
Действия: правка, уведомление Разработчику, запись в WORK_LOG.md, проверка сборки.

## Ошибки и восстановление
- Установка или команда не прошла: BLOCKED, запись в WORK_LOG.md, повтор после исправления.
- Запрос без ответа дольше одного цикла проверки: эскалация пользователю через TASK_BOARD.md.
- Конфликт между агентами: CONFLICTS.md, решение пользователя.
- Если сессия прервалась, при следующем запуске восстанови состояние из TASK_BOARD.md и WORK_LOG.md.
